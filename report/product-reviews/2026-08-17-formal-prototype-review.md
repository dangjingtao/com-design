# 核心产业学院 App 原型正式评审稿 — 2026-08-17

> 状态：Formal Review / 周一会议版  
> 背景：周五下午已完成一轮完整过稿；本稿基于周五初审、周末产品背景补充及第二轮复核形成。  
> 范围：当前 Mockplus 原型（约 140 个页面/状态）及其对应产品结构、关键业务闭环、交互正确性与 Com Design 一致性。  
> 目标：周一不再重复逐页浏览，而是完成结构确认、问题分级、下一版修改范围与责任边界确认。

---

## 0. 评审结论摘要

当前原型已经覆盖了赛事、报名、课程、权益、企业、实习、可信项目、AI 陪跑和学生资产等主要能力，问题不在“功能太多”，而在于：

> **平台需要从“能力并列”进入“产品骨架收敛”阶段。**

现阶段最重要的不是继续增加页面，而是把学生核心需求、赛事生命周期、就业机会与长期资产之间的关系表达清楚。

本轮确认后的学生核心需求为：

1. **参赛**；
2. **就业 / 实习。**

其中两者并不完全对称：就业是学生天然存在的需求；参赛需求则需要平台提供足够有价值、有影响力、值得投入的赛事，并通过真实运营形成吸引力。赛事不能只被做成“比赛资讯列表”，而应成为完整业务。

因此下一版原型应优先完成：

- 首页围绕“参赛 + 就业”重新建立主叙事；
- 公共平台与赛事生命周期内能力分层；
- 明确 App 长期账号、赛事身份/运营权限、赛事项目和长期资产之间的边界；
- 修复仍然有效的 P0 交互与状态问题；
- 最后再进行 Com Design 视觉收口。

## 1. 已确认的产品背景与边界

### 1.1 产品定位

产品不是单一“三创赛 App”，而是面向创新创业学生的平台。

- 三创赛是首批用户来源，也是当前最急迫的业务入口；
- 未来可承载其它赛事；
- 平台长期价值不能被单一赛事生命周期绑死；
- 当前学生侧最核心的两条需求是 **参赛 + 就业 / 实习**；
- 权益、课程、企业、资料、可信成果和 AI 能力用于增强这两条主线，并承担运营与商业价值。

### 1.2 参赛需求必须被“做重”

学生并不会因为平台存在一个“热门赛事”栏目就形成稳定参赛需求。

参赛业务需要完整承接：

```text
发现值得参加的赛事
  -> 理解赛事价值、规则和门槛
  -> 报名
  -> 学校审核真实性
  -> 获得赛事身份 / 权限
  -> 参赛项目与赛事陪跑
  -> 成绩 / 证书 / 成果
  -> 比赛结束
  -> 经历与成果沉淀到长期账号
```

因此“比赛机会”不是资讯栏目，而是正式赛事对象的发现入口。

### 1.3 App 账号长期存在，赛事权限有生命周期

普通学生可以注册并长期使用 App，即使当前没有任何赛事身份，也可以访问平台公共能力。

同一个 App 账号未来可以关联多个赛事身份。

但赛事侧身份、运营账号或赛事专属权限存在生命周期。比赛结束后，可以按规则回收相应赛事运营权限。

应明确区分：

```text
App 学生账号：长期存在
Competition Identity / 赛事权限：按赛事生命周期存在
赛事项目：服务该次赛事生命周期
长期资产：比赛结束后继续存在
```

### 1.4 项目不是永久运营对象，项目经历才是长期资产

本轮修正一个重要判断：

**学生的参赛项目主要存在于对应赛事生命周期内，不需要默认设计成赛后仍持续运营的长期项目管理对象。**

比赛结束后，真正需要长期保留的是：

- 参赛经历；
- 项目经历摘要；
- 团队角色；
- 比赛成绩；
- 获奖证书 / 可信成果；
- 对应课程与学习成果。

因此更准确的关系是：

```text
赛事期间：赛事身份 -> 参赛项目 -> 创赛工坊 / 任务 / 课程 -> 比赛结果

赛事结束：赛事权限回收 -> 项目运营结束 -> 经历 / 成绩 / 证书沉淀到学生长期账号
```

### 1.5 三创赛报名边界

当前最急业务是三创赛学生报名，但 App 不建议重复建设一套完整复杂报名表单。

已形成的方向：

- App 学生账号作为身份绑定锚点；
- 未报名学生可调用现有 PC 响应式报名层；
- 报名完成后，结果回流 App；
- App 原生展示报名状态、赛事身份、团队信息及后续赛事能力。

因此当前原型中的原生报名页面必须先做“有效范围确认”，不要一边保留响应式方案，一边继续完整维护两套报名流程。

### 1.6 学校老师属于后台运营角色

当前真实运营链路为：

```text
运营企业
 -> 联系学校电商相关老师
 -> 为学校老师开设账号
 -> 老师通过学生会 / 社团等渠道推动报名
 -> 学生报名
 -> 学校老师审核学生报名真实性
```

学校老师不进入学生 App，适合使用 Web / 运营后台。

当前学校侧产品重点是：

- 授权赛事范围；
- 授权学校范围；
- 报名真实性审核；
- 必要的校内赛事运营协同。

暂不需要扩张为学校独立门户或完整校园 SaaS。

### 1.7 企业在学生侧的核心心智

企业不应首先被设计成“招聘公司”。

更符合当前业务的学生侧心智是：

1. **赛事、权益、课程、活动等资源的提供者；**
2. **值得长期关注的品牌 / 合作方。**

实习和招聘是企业与学生关系深化后的一部分。

因此企业详情页未来应优先表达企业与赛事、权益、课程、活动及机会之间的真实关系，而不是默认以职位列表为核心。

### 1.8 企业侧商业逻辑

平台不是单纯依靠学生付费的 C 端产品。

企业投入赛事、权益、课程、实习等资源，可以获得：

- 学生与项目触达；
- 品牌与社会影响；
- 优秀人才发现机会；
- 与更多合作企业、资源方建立连接的机会。

当前最明确的人才发现信号是 **比赛成绩**。平台不需要为了筛选人才额外构造隐藏 AI 评分或复杂人才分层机制。

学生是否接受后续实习或岗位机会，始终由学生自主选择；“发现少量高潜人才”属于运营收益，不应被设计成强制产品 KPI。

### 1.9 可信项目 / 可信认证不能按低频简单降权

可信项目同时存在两条价值轴：

- 学生侧：证书、成果、赛事经历及履历表达；
- 公司侧：教育部相关认证 / 背书带来的平台权威叙事、合作信用和赛事承接能力。

因此它即使不是学生高频使用能力，也不能仅按 DAU 或点击率判断优先级。

但对外出现“教育部认证”“法律效力”等强表述时，仍需要以正式授权材料确认适用范围，避免有价值的背书因表述越界产生风险。

### 1.10 创赛工坊的边界

创赛工坊当前首先是三创赛的赛事 AI 陪跑能力，尤其服务美妆电商 / 新零售赛道的参赛过程。

它不是首期需要抽象为全平台通用 AI 助手的能力。

比赛具体时间可能由学校、省份、赛道在官方窗口内自行安排，平台是否能稳定获取精确节点尚未确认。因此首版不应强依赖精确比赛日。

## 2. P0：正式评审前必须确认或修复的问题

### P0-1 报名流程先做有效范围裁剪

原型存在“报名答题提交后跳入课程成就”等明显错误交互，但在修复前必须先确认哪些原生报名页面仍然有效。

处理顺序：

1. 标记继续保留的 App 原生报名页面；
2. 被 PC 响应式报名替代的页面归档 / 移出开发范围；
3. 只对保留链路重新验收跳转、状态与回流。

**验收标准：** 不再同时存在两套互相冲突的正式报名流程。

### P0-2 创赛工坊 S1-S6 交互串线

当前多个技能任务页面存在复制后遗留的错链 / 串线问题，属于仍然有效的 P0。

工坊既然是三创赛核心赛事能力，必须保证：

- 每个任务进入正确步骤；
- 确认页与任务对应；
- 进度和成果归属正确；
- 返回路径不串到其它技能任务。

研发实现应尽量使用统一任务模型，而不是六套页面逻辑分别复制。

### P0-3 “任务专区”当前缺业务定义

首页已有“任务专区”，但目标页面为空；同时创赛福利下已有“日常任务 / 核心任务”。

正式开发前必须先确认“任务专区”的业务对象是什么：

- 平台成长任务；
- 赛事任务；
- 运营活动任务；
- 或其它类型。

未定义前不建议继续补 UI。

## 3. P1：产品结构与信息架构问题

### P1-1 首页主叙事与学生核心需求不一致

当前首页大量注意力被以下内容占据：

- 学力值；
- 学习数据；
- 课程；
- 任务；
- 三创能力；
- 多个工具型金刚区入口。

而学生两条核心需求“参赛 + 就业 / 实习”并没有成为第一层叙事，尤其实习机会被埋在较深位置。

下一版首页优先级建议改成：

```text
第一层：值得立即行动的事情
- 当前 / 推荐赛事
- 实习 / 就业 / 企业机会

第二层：我的赛事状态
- 已报名 / 进行中赛事
- 赛事关键状态
- 对应赛事专属能力

第三层：成长与资源支撑
- 课程
- 权益
- 企业资源
- 可信成果
- 资料
```

这不是要求立即套用固定版式，而是先把信息优先级纠正。

### P1-2 公共平台与赛事生命周期能力需要分层

目前很多全局入口与赛事专属能力混在一起。

建议至少在产品模型上明确：

**公共平台层**
- 赛事发现；
- 实习 / 就业机会；
- 企业；
- 通用权益；
- 公共课程 / 资料；
- 我的长期资产。

**赛事生命周期层**
- 报名 / 审核 / 参赛身份；
- 参赛项目；
- 赛事专属课程 / 权益 / 资料；
- 创赛工坊；
- 赛事任务；
- 成绩 / 证书。

当前不要求一次性设计很重的“赛事空间 UI”，但数据、权限和入口必须能表达这个边界。

### P1-3 “社区”名称与实际业务不匹配

当前“社区”内部实际承载：

- 公告 / 品牌资讯；
- 企业；
- 实训 / 实习机会。

但没有典型论坛、UGC、用户动态等社区能力。

更重要的是，“企业 + 就业机会”本身属于学生核心需求之一。

因此不建议继续用“社区”这个词反向约束产品。下一版应先按“企业 / 机会”场景重新组织，再确认最终命名。

### P1-4 “学院”是否长期占一级导航需要重新验证

课程系统很重要，但系统重要并不自动等于必须占底部一级导航。

既然学生核心需求已经明确为参赛与就业，课程更接近支撑参赛、成长和长期履历的能力。

周一建议确认：

- “学院”是否继续占一级导航；
- 或课程通过首页、赛事空间和“我的”获得足够强入口。

本稿不预设删除结论，但要求重新按核心任务竞争一级导航权重。

### P1-5 创赛工坊必须体现赛事归属

当前工坊入口与可信空间、福利、成绩查询等全局能力并列，容易让用户理解成平台通用 AI。

下一版至少要明确：

- 工坊属于哪个赛事；
- 无对应参赛身份用户看到什么状态；
- 赛事结束、权限回收后如何处理历史成果。

### P1-6 工坊首页需要强化“下一步做什么”

当前工坊同时展示阶段、算力、运行中任务、成果、技能推荐、技能矩阵等较多内容。

作为赛事陪跑产品，进入后第一主动作应该更明确：

> **我现在最该做什么？**

建议强化：

- 继续当前任务；
- 下一步建议；
- 当前需要补充的材料；
- 未完成关键动作。

算力、技能矩阵等信息作为支撑层。

### P1-7 企业模块应从“企业名录”升级为资源关系表达

企业详情不应只展示企业介绍或招聘岗位。

应逐步表达企业关联的：

- 赛事；
- 权益；
- 课程；
- 活动；
- 实习 / 就业机会。

这样才能形成“值得关注的品牌 / 合作方”心智。

### P1-8 可信项目保持高商业权重，但避免成为孤岛

可信项目需要有足够展示权重，但最好与真实学生成果和赛事数据连接：

- 比赛成绩；
- 证书；
- 项目经历；
- 学习成果；
- 平台履历。

高权重不等于单独建立一套与其它学生资产割裂的体系。

## 4. P2：Com Design 与视觉一致性

视觉问题成立，但优先级低于产品结构和 P0 流程正确性。

### P2-1 字号与字体需要语义化收口

原型存在大量 8px、10px、15px、17px 等一次性字号，并混用字体。

下一版应映射到 Com Design 的语义文本角色，尤其避免使用过小字号承载正文和关键信息。

### P2-2 阴影使用过重

普通 Card、List、Button 大量依赖阴影建立层级，与 Com Design Flat-first 原则不一致。

优先通过 surface、border、spacing、typography 建立层级。

### P2-3 触控区域需要满足真实移动端标准

16/18/24px 图标可以作为视觉尺寸，但不能直接等于点击区域。

实现需保证 iOS 约 44pt、Android 至少约 48dp 的有效触控区域。

### P2-4 Radius 和一次性视觉值需要回收

避免继续按页面产生大量 2/3/5/11/19/20/24 等孤立圆角和视觉值，应映射回 Com Design token / component 体系。

## 5. 三条核心业务链路

### 5.1 学生公共平台链路

```text
注册 / 登录
 -> 浏览值得参加的赛事
 -> 浏览企业与就业 / 实习机会
 -> 使用通用权益、课程、资料
 -> 维护长期个人资产
```

没有赛事身份时仍然成立。

### 5.2 三创赛参赛生命周期

```text
App 学生账号
 -> 进入三创赛报名
 -> PC 响应式报名
 -> 学校老师后台审核真实性
 -> 报名成功 / 获得三创赛身份与权限
 -> 参赛项目
 -> 创赛工坊 / 赛事课程 / 任务 / 权益
 -> 比赛成绩 / 证书 / 可信成果
 -> 赛事结束
 -> 回收赛事运营权限
 -> 参赛经历、项目经历摘要、成绩、证书沉淀到长期账号
```

### 5.3 就业 / 实习链路

目标方向为平台内承接，而不是只做外链资讯：

```text
岗位 / 实习发现
 -> 机会详情
 -> 使用长期平台简历
 -> 平台内投递
 -> 投递记录
 -> 状态跟踪
```

长期简历可以吸收已确认的赛事经历、成绩、证书、课程成果等，但由学生确认和编辑最终表达。

## 6. 周一正式评审需要拍板的事项

周五已经完整过稿，周一不建议再次逐页从头浏览。会议应围绕以下决策项确认：

| # | 决策项 | 需要确认的结果 |
|---|---|---|
| 1 | 首页第一层主叙事 | 是否确认“参赛 + 就业 / 实习”为学生核心任务 |
| 2 | 公共平台 / 赛事层 | 是否确认赛事专属能力按赛事身份与生命周期管理 |
| 3 | 报名范围 | 哪些 App 原生报名页保留，哪些由响应式报名替代并归档 |
| 4 | 创赛工坊入口 | 无赛事身份时隐藏、锁定展示，还是作为赛事转化入口 |
| 5 | 一级导航 | “社区”“学院”是否继续占当前一级位置，或重新组织企业 / 机会 / 课程 |
| 6 | 任务专区 | 明确业务定义及与创赛福利任务的关系 |
| 7 | 赛事时间 | 学校 / 省份 / 赛道的精确赛程是否存在稳定数据源 |
| 8 | 可信项目 | 确认对外展示权重与正式认证 / 授权文案边界 |

会议中其它页面级问题，如不影响上述结构，可进入会后问题清单，不在现场无限发散。

## 7. 下一版原型交付范围建议

下一版不建议“把 140 张页面全部精修一遍”。

推荐先完成四类交付：

### A. 信息架构与导航

- 公共平台主导航；
- 赛事上下文入口；
- 首页信息优先级；
- 企业 / 就业 / 课程的位置。

### B. 三条母链路

- 注册 / 报名 / 审核 / 获得赛事身份；
- 三创赛参赛生命周期；
- 就业 / 实习发现与投递。

### C. P0 有效页面修复

- 删除 / 归档被替代流程；
- 修正创赛工坊 S1-S6 串线；
- 明确任务专区后再补交互；
- 补齐权限、空状态、异常状态。

### D. Com Design 收口

只在上述结构稳定后进行：

- typography；
- spacing；
- radius；
- surface / border；
- interaction target；
- component mapping。

---

## 8. 下一版验收标准

下一版评审不以“新增多少页面”为目标，至少满足：

1. 学生第一次进入 App 能理解平台主要提供 **参赛 + 就业 / 实习**；
2. 无赛事身份用户也能正常使用公共平台；
3. 三创赛参赛身份和专属能力有明确生命周期；
4. 报名不再存在两套互相冲突的正式实现；
5. 创赛工坊有效任务不串线，并且能告诉用户“下一步做什么”；
6. 比赛结束后，赛事权限可回收，但参赛经历、成绩、证书等长期资产仍可访问；
7. 企业被理解为资源 / 机会 / 品牌合作方，而不仅是招聘列表；
8. 可信项目既有商业展示价值，也能与真实成果发生连接；
9. 一级导航和首页不再用课程 / 学力数据压过学生核心任务；
10. 关键移动端页面符合 Com Design 的基础文本、层级与触控规范。

---

## 9. 正式评审结论

> **当前原型已经具备平台所需的大部分能力组件，下一阶段不应继续以“增加模块、增加页面”为主，而应围绕“参赛 + 就业”建立学生主任务，用赛事生命周期组织报名、项目、创赛工坊、成绩与证书，用长期账号承接赛后的经历与成果；同时保留可信项目的对外商业背书价值。周一正式评审的重点应从逐页看稿转为结构拍板和下一版范围确认。**
