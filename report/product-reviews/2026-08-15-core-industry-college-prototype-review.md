# 核心产业学院 App 原型评审 — 2026-08-15

> 状态：Draft / 持续评审（第二轮，已补充业务背景）

> 评审基线：产品定位、平台架构、关键业务闭环、交互正确性、Com Design 一致性与研发落地风险。

## 0. 本轮先修正评审前提

第一轮评审过早从原型本身反推产品结构，缺少业务背景，因此把“模块很多”偏快地解释成了产品膨胀。补充背景后，这个判断需要修正。

当前产品不是单一“三创赛 App”，也不是泛大学生生活平台，而是：

> **面向创新创业学生的长期平台。三创赛是第一批用户和当前最急业务入口，但平台必须能够继续承载其它赛事，并通过比赛机会、实习机会以及课程、权益、企业、资料和 AI 陪跑形成长期使用价值。**

因此，注册登录、赛事、课程、权益、企业并非“多余模块”，而是需要建设的平台级底座。真正需要评审的是：**原型是否已经把这些底座组织成一个清晰的产品。**

## 1. 已确认的业务背景 / 评审约束

以下内容作为后续评审基线。

### 1.1 产品定位

- 产品核心人群：创新创业学生，而不是所有大学生泛人群。
- 三创赛是 App 第一批用户来源，但未来会承载其它赛事。
- 企业方是当前主要运营方。
- 对学生长期粘性最重要的两个场景，当前排序为：
  1. **比赛机会**；
  2. **实习机会**。
- 权益、课程、资料、企业内容、AI 能力等，是长期价值的重要增强层。

### 1.2 公共平台与赛事空间

普通学生即使没有任何参赛身份，也可以注册和长期使用 App，并看到平台基础信息，包括比赛机会、通用权益、资料、企业/实习机会等。

同一个 App 账号可以拥有多个赛事身份。由于赛事类型、规则、流程和能力不同，学生可以明确感知自己进入了哪个赛事。

当前更合理的产品假设是：

```text
公共平台
├─ 比赛机会
├─ 实习 / 企业机会
├─ 通用权益
├─ 通用资料 / 内容
├─ 课程与长期学习资产
└─ 我的

赛事空间（可多个）
├─ 赛事信息 / 赛程
├─ 报名状态 / 团队
├─ 赛事专属资料
├─ 赛事专属权益
└─ 赛事专属能力（例如三创赛的“创赛工坊”）
```

这里暂时不把“独立赛事空间”的交互形式写死，但数据和权限模型不能继续假设“一个账号 = 一个赛事”。

### 1.3 账号与赛事身份

方向已明确：**App 账号优先，赛事身份绑定到 App 账号。**

一个学生可以拥有多个赛事身份。赛事身份决定某些专属资源和权限。

特别是当前“创赛工坊”属于三创赛运营能力：无三创赛参赛身份的学生不允许使用对应赛事 AI 能力。

因此建议把身份关系理解为：

```text
User / App Account
  └─ CompetitionIdentity[]
       ├─ competitionId
       ├─ participant/team role
       ├─ registration status
       ├─ validity / lifecycle
       └─ competition-scoped permissions
```

这比把“三创赛参赛者”写进全局账号类型更安全。

### 1.4 报名系统边界

当前最急业务仍然是三创赛学生报名，但此前评审已形成一个重要原则：

- App 不鼓励重复实现复杂报名表单；
- 未报名学生可以调用现有 PC 响应式报名层；
- App 登录账号应优先成为身份绑定锚点；
- 完成报名后，App 原生展示报名信息、赛事身份、团队和后续能力。

因此，原型中现有“基础信息填写（队长/队员）—报名答题—添加成员”等完整原生报名链路，**需要先确认哪些仍属于有效设计，哪些已被响应式报名方案替代**。

在这个边界确认之前，不建议研发同时维护两套报名实现。

### 1.5 企业系统

企业可能同时扮演：

- 赛事主办/承办/合作方；
- 权益供给方；
- 课程供给方；
- 实习 / 岗位供给方。

学生可以关注企业，以持续获得权益、活动和实习机会。

现阶段企业内容仍主要由平台运营方直接管理，不急于先做完整企业自运营后台；但企业作为业务主体的数据模型应保持独立，以便未来形成商业闭环和逐步开放运营权限。

### 1.6 权益系统

权益不是单一“积分商城”。至少需要支持：

- 全平台通用权益；
- 某赛事专属权益；
- 企业 / 活动定向权益。

后续资格规则还可能继续组合赛事身份、地区、学校等条件，因此权益系统需要与身份/资格判断解耦，而不是把规则写死在页面入口。

### 1.7 课程系统

课程首期优先服务三创赛，但不能只服务三创赛。

学习进度、完课记录、考试/成绩、证书等需要长期保留。关键原则是：

> **赛事有生命周期，学生学习资产没有。**

课程可以来自赛事，也可以逐步成为平台通用内容；赛事结束不能导致用户长期学习资产丢失或不可访问。

### 1.8 创赛工坊

“创赛工坊”当前不是全平台抽象 AI 助手，而是面向三创赛运营的赛事 AI 陪跑产品，尤其聚焦美妆电商/新零售赛道，目标是覆盖参赛全生命周期。

当前已知的重要限制：官方通常给出时间窗口，但学校、省份和不同赛道可能在窗口内自行安排具体比赛时间。平台是否能稳定获得各学校/省份/赛道的精确赛程，目前未知。

因此首版工坊不能依赖“平台一定知道学生具体比赛日”这个假设。

更稳妥的是：

```text
官方时间窗口
+ 可选的学校/省/赛道精确节点
+ 学生/团队当前项目状态
```

有精确节点时增强倒计时和提醒；没有时仍能完成陪跑。

### 1.9 学生数据 / 画像

“高级画像系统”当前更接近愿景，不应作为已经具备的技术能力写进首期依赖。

较可靠的落地路径是：

- 注册时收集少量基础资料；
- 报名时获取赛事相关资料；
- 创赛工坊通过系列问卷继续补充项目状态和需求；
- 已采集字段尽量全平台复用，避免不同模块重复询问。

行为自动画像、推荐算法可以后置。

## 2. 第二轮核心结论

### 2.1 最大问题不是“模块多”，而是产品主轴尚未被首页和一级导航表达出来

首页当前主要结构为：

```text
任务专区 / 创赛工坊 / 三创赛专区 / 成绩查询
可信空间 / 创赛福利 / 三创同学会
学力值与学习数据
热门赛事
热门课程
```

底部导航仍是：

```text
首页 / 赛事 / 学院 / 社区 / 我的
```

在真实产品定位下，这个结构存在一个非常明显的错位：

> **业务认为长期粘度最高的是“比赛 + 实习”，但原型首页几乎没有实习机会；实习被埋在名为“社区”的一级模块中。**

相比之下，课程、学力值、证书、任务占据了大量首页面积，导致用户第一眼更容易把产品理解成“赛事培训/学习平台”，而不是创新创业学生的平台。

这是目前最应该修的产品叙事问题。

### 2.2 “社区”承担的是核心业务，却用了最弱、最误导的名字

当前社区内部实际上是三个入口：

```text
公告广场 / 企业列表 / 实训机会
```

其中“企业 + 实训/实习”恰恰是平台长期粘性的核心之一。

因此问题不是简单把“社区”换个词，而是需要重新判断这个一级入口的用户任务：它到底是资讯区，还是学生寻找企业与实习机会的核心场域。

目前的内容结构已经明显偏后者，“社区”会让用户错误期待论坛、动态、UGC。

**建议下一版先按“机会场”重新组织内容，再决定最终命名。**

### 2.3 “学院”作为一级导航的权重需要重新验证

课程系统本身很重要，而且学习结果是长期资产；但“系统重要”不等于“必须占一个底部一级入口”。

在当前用户粘性排序里，课程并不是前两位，而比赛和实习是。

因此要重新验证：

- 课程是否需要长期占据底部一级导航；
- 还是作为赛事成长、能力提升和个人长期资产的一部分，在首页/赛事/我的中有强入口即可。

这里暂不直接给出删除“学院”的结论，但它已经需要拿真实优先级重新竞争一级导航席位。

### 2.4 “三创赛专区”方向正确，但不能成为未来平台架构里的硬编码特例

首页出现“三创赛专区”说明原型已经开始表达赛事上下文，这是正确方向。

但未来同一个学生可能同时参加多个赛事。因此需要避免形成：

```text
首页固定功能入口 = 三创赛专区
```

更可扩展的模型应该是“我的赛事 / 当前赛事”作为动态对象，三创赛只是首期实例。

例如：

```text
我的赛事
- 第十六届三创赛 · 进行中
- XX 创新创业赛 · 已报名
```

进入赛事后再显式展示该赛事自己的能力。

### 2.5 创赛工坊应该被明确识别为“三创赛空间内的专属能力”

当前首页把“创赛工坊”与可信空间、成绩查询、福利等一起当作全局金刚区能力，会弱化它的权限和赛事上下文。

而业务已经明确：无三创赛参赛身份的学生不能使用该赛事 AI。

因此下一版要明确至少两件事：

1. 工坊入口如何体现赛事归属；
2. 无对应赛事身份时是隐藏、展示但不可使用，还是作为赛事营销入口。

这个规则需要产品决定，不能由研发临时判断。

### 2.6 首页学习数据占位过重，与当前产品定位不匹配

首页目前直接展示：

- 学力值；
- 在学课程；
- 学习时长；
- 已完成；
- 获得证书；
- 热门课程。

如果产品最终定位是创新创业学生平台，这些内容仍然有价值，但更像**成长资产和能力支撑**，不应该自然压过实习机会。

建议首页信息层级重新排序为：

```text
第一层：当前最值得行动的机会
  - 比赛
  - 实习 / 企业机会

第二层：与我正在进行的赛事有关
  - 我的赛事
  - 三创赛 / 其它赛事状态
  - 对应赛事专属能力

第三层：长期成长和运营能力
  - 课程
  - 权益
  - 资料
  - 学习资产 / 证书
```

不是要求按这个版式直接画，而是先把优先级倒过来。

## 3. 原型中需要重新定性的旧问题

### 3.1 原“报名链路 P0”需要先判断是否仍属于有效流程

第一轮发现“报名答题”页面存在跳入课程成就模块的错误。

该交互错误本身仍然存在，但现在不能简单要求“修好整套原生报名流程”，因为业务已经倾向复用响应式报名层。

因此处理顺序应改为：

1. 标记哪些原生报名页面继续保留；
2. 被响应式报名替代的页面从有效开发范围移除/归档；
3. 只对保留链路重新验收交互。

不要修一套准备废弃的流程。

### 3.2 创赛工坊 S1-S6 串线仍是有效 P0

工坊多个 S1/S2/S3/S4/S5/S6 页面仍有复制后交互串线问题。

这部分仍然需要优先处理，因为工坊是明确在继续建设的三创赛核心能力。

研发模型建议保持：

```text
TaskDefinition -> TaskRun -> Step -> Artifact
```

不要把 S1-S6 理解成六套互相复制的硬编码页面。

### 3.3 “任务专区”仍然缺业务定义

首页已有“任务专区”，但对应页面为空。

同时创赛福利下已有“日常任务 / 核心任务”。

现在不建议直接推导统一任务引擎，因为业务背景尚未说明“任务专区”究竟想解决什么。

这一项保留为产品问题，等待确认后再设计。

## 4. 创赛工坊专项评审

### 4.1 工坊已经有“全生命周期陪跑”的骨架

当前原型包含：

- 当前阶段；
- 算力；
- 运行中任务；
- 最近成果；
- 技能推荐；
- 六大技能包；
- 项目洞察、诊断、内容运营、数据复盘、赛事冲刺、职业规划；
- 动态答题、生成确认、任务进度、成果详情。

这与“赛事陪跑”的定位基本一致，不应该退回成一个普通 AI 聊天页。

### 4.2 当前阶段文案存在“精确赛程假设”风险

原型直接展示：

```text
当前阶段
比赛初期阶段
2026.08.06 - 2026.08.20 · 距截止还有14天
```

但实际赛程可能由学校、省份、不同赛道在官方窗口中自行安排。

如果平台拿不到学生所在学校/省/赛道的具体节点，这种精确倒计时容易制造错误确定性。

建议产品模型区分：

- 官方窗口；
- 本校/本赛道赛程（若已录入）；
- 团队当前项目进度。

三者不要混成一个“当前阶段”。

### 4.3 陪跑主动作还不够突出

当前工坊首页同时展示算力、运行中、最近成果、技能推荐、阶段、技能矩阵等很多信息。

对于陪跑产品，用户进入后的第一问题应是：

> **“我现在最该做什么？”**

建议后续强化“继续当前任务 / 下一步建议 / 当前待补材料”这类主动作，再把算力和技能矩阵作为支撑信息。

## 5. 系统级建设建议

### 5.1 五个重要系统都按平台级模型建，但排期不等于同时做满

业务已经明确重要底座：

```text
账号/注册登录
赛事
课程
权益
企业
```

原则是：**模型按平台级建设，功能按当前业务优先级交付。**

当前三创赛报名最急，不意味着把账号/赛事模型写死到三创赛；同样，企业未来可以自运营，也不意味着现在就先造完整 B 端。

### 5.2 建议先把四类关系钉死

相比继续补 UI，更值得先让产品和技术确认：

```text
User <-> CompetitionIdentity
Competition <-> Course / Benefit / Material / AI Capability
Enterprise <-> Competition / Benefit / Course / Internship
User <-> LongTermAsset (course progress / certificate / history)
```

只要这四类关系清楚，后面很多页面自然会变简单。

### 5.3 问卷不是“画像系统”，而是统一字段的采集工具

短期建议避免“大画像平台”表述。

把真实可交付能力说清楚：

- 按场景收集；
- 已有字段自动带入；
- 数据全平台复用；
- 不重复问用户已经明确提供的信息；
- 后续有能力再增加自动标签/行为画像。

这比先做一个抽象画像系统更可靠。

## 6. Com Design 一致性问题（第二优先级）

这些问题仍然成立，但不应抢在产品结构前面大面积处理。

### 6.1 字体与字号自由度过高

原型大量使用 8px、10px、15px、17px 等一次性字号，并混用 Microsoft YaHei 与 PingFang SC。

下一轮应从逐页面调字号改成语义文本角色映射，尤其避免 8/10px 承载真实正文和关键信息。

### 6.2 阴影使用超出 Flat-first 原则

普通 Card / List / Button 大量依赖阴影形成层级，后续应回到 surface、border、spacing、typography 优先。

### 6.3 小图标必须有足够真实触控区

原型视觉节点存在大量 16/18/24px 操作图标。实现侧必须保证 iOS/Android 真实 hit target，不把视觉尺寸直接当点击尺寸。

### 6.4 Radius 和视觉值仍需回收进语义系统

避免继续按页面手调 2/3/5/11/19/20/24 等一次性圆角值。

---

## 7. 下一轮原型建议优先级

不要按 140 张页面逐张精修，建议按以下顺序：

### P0 — 产品骨架

1. 明确公共平台 vs 赛事空间；
2. 明确多赛事身份和权限；
3. 明确报名响应式层与 App 原生边界；
4. 首页重新围绕“比赛 + 实习”建立第一层叙事；
5. 重新定义“社区”承担的机会/企业任务。

### P1 — 核心业务闭环

1. 三创赛赛事空间；
2. 创赛工坊身份、阶段和任务模型；
3. 企业—实习机会；
4. 通用/赛事权益；
5. 课程长期资产。

### P2 — 页面与视觉收口

1. 清理已废弃原型链路；
2. 修复有效链路串线；
3. 映射 Com Design tokens/components；
4. 处理真实内容、空状态、异常状态和权限状态。

## 8. 当前需要继续确认的问题

以下问题不在文档里预设答案，按产品讨论逐个确认：

1. **无三创赛身份的学生，在首页看到“创赛工坊”时应该是什么状态：完全隐藏、可见但锁定，还是作为赛事招募入口？**
2. “任务专区”到底承担平台成长任务、赛事任务、运营活动任务，还是其它东西？
