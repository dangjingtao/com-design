# T0 — 所有施工线程开工前置任务

> 适用范围：T02 / T03 / T04 / T05、返修线程以及任何直接修改 `prototype/core-industry-college/` 的施工线程。
> 性质：**开工门禁**。先完成 T0，再进入自己的业务任务卡。
> T0 默认只读、只核对，不产出业务 UI；没有发现真相源问题时不需要单独提交代码，也没有独立 R0。

## 0. 先确认自己是谁

开工前必须明确：

- 当前执行的是哪张任务卡 / 哪个返修项。
- 本线程允许修改什么，不允许碰什么。
- 上一张评审卡是否已经 PASS；若未 PASS，不得越级施工。
- 当前分支必须是 `core-industry-college-refactor`，并确认开始施工时的 HEAD。

如果施工期间分支 HEAD 被其它线程推进，**在改共享文件前重新读取最新版本**，禁止按旧上下文覆盖别人的提交。

## 1. 必读真相源

按顺序阅读：

1. `00-master-outline.md`
2. `10-task-cards.md` 中自己的任务卡
3. `20-review-cards.md` 中对应评审卡
4. `01-t01-page-map-routing-baseline.md`
5. `01-t01-old-new-map.tsv` 中与本任务有关的旧页
6. 最近已经 PASS 的上游评审 / 实现报告
7. 当前 `prototype/core-industry-college/` 实际代码
8. 与本任务有关的旧 Mockplus 页面 / interaction 证据
9. `design.md`、`design-source/` 中实际需要的 Com Design 组件与 token

原则：**不能只读任务卡就开写。代码现状也是当前真相源的一部分。**

## 2. 开工前必须形成 8 项理解

施工线程在真正写代码前，必须能明确回答：

1. **本卡目标**：这一轮到底解决什么用户问题。
2. **范围边界**：哪些属于本卡，哪些必须留给其它任务卡。
3. **进入动线**：用户从哪里进入本卡负责的区域。
4. **完成动线**：主动作完成后去哪里，怎么返回。
5. **关键状态**：至少列出 happy path 之外必须支持的 pending / empty / error / permission / ended 等状态。
6. **上游冻结契约**：哪些 route / state / provider / domain 语义不能自行推翻。
7. **待决策项**：D01–D11 或其它未拍板事项中，哪些与本卡有关；不得自行补产品定义。
8. **预计改动面**：准备改哪些目录 / 共享文件，为什么必须改。

任何一项答不出来，先继续阅读，不要直接施工。

## 3. 代码侦察

至少检查：

- `src/routes/registry.ts`：已有语义路由，不重复另起一套路由。
- `src/state/model.ts`：T01 共享状态契约。
- `src/mock/scenarios.ts`：已有场景，不重新发明冲突 fixture。
- 已有 Provider / shared state：优先增量接入，不建立平行账号/赛事状态源。
- `src/components/`：已有共享 UI 能复用则复用。
- `src/features/`：确认其它施工线程已经实现到哪里。

特别禁止：

- 再造第二套 account / competition identity / current workspace 模型。
- 用页面内临时 state 假装完成跨页面业务状态。
- 为一个新页面复制已有整页代码再改文案。
- 为了“方便自己”重构与本卡无关的共享基础设施。

## 4. 旧原型理解

只抽取与本任务相关的旧页：

- 功能必须有去向。
- 字段、状态、入口、动作需要保留证据。
- 旧原型中的明显错链 / 悬空 target **不得照抄**。
- 页面可以合并或状态化，不要求一旧页对应一新页。

发生冲突时遵守总纲优先级：

**功能是否存在看旧原型；功能放哪里、怎么串看正式评审/T01；怎么呈现看 Com Design。**

## 5. 动线预演

开工前至少在文字层面走一遍本卡关键路径：

`入口 -> 页面/状态 -> 主动作 -> 下一步 -> 结果 -> 返回/继续`

同时检查：

- 未登录怎么办。
- 无权限怎么办。
- 数据为空怎么办。
- 操作失败怎么办。
- 业务结束 / 赛事结束怎么办。
- 从其它模块进入后，返回是否回正确来源。
- 多赛事账号进入赛事 A 后，深层页是否始终保持赛事 A context。

**如果需要靠“回首页再找一次入口”才能继续，先修 Flow，再写 UI。**

## 6. Com Design 预检

施工前列清：

- 可以直接复用的 Core 组件。
- 需要新增的少量 Product Pattern。
- 使用哪些已有 semantic token。

规则：

- 不修改 Com Design Core 真相源。
- 不因为中保真就随意写一套新字号 / 圆角 / 颜色体系。
- 不为了视觉效果引入复杂品牌物料。
- 先保证结构、交互、状态，再做视觉收口。

## 7. 并行施工安全规则

多个施工线程同时工作时：

- 只修改自己任务域内的文件。
- 必须改共享文件时，只做最小增量，并在交付说明中明确原因。
- 不 force push、不 reset 别人的提交、不 squash 与自己无关的 commit。
- 不覆盖近期由其它线程更新过的共享文件；先读取最新 HEAD 再改。
- 如果共享 route/state contract 确实必须改变，**停止并提交给评审线程判断**，不要自行破坏上游冻结契约。
- 遇到与其它线程同一业务对象的职责交叉，优先做明确 handoff，不同时实现两套。

## 8. 验证基线

施工前确认本环境能做哪些验证，施工后按能力真实执行：

- TypeScript compile / type check。
- 路由是否匹配。
- mock/state 是否能重现关键状态。
- 关键动线静态检查或浏览器 walkthrough。
- npm 安装 / Vite build（环境允许时）。

环境不允许的项目明确写“未验证”，**禁止把未运行写成已通过**。

## 9. T0 完成标准

进入正式施工前，线程应在对话中给出一个很短的开工摘要，至少包含：

```text
T0 DONE
任务：Txx
范围：...
上游冻结契约：...
关键动线：...
关键状态：...
未决项：...
预计改动：...
当前 HEAD：...
```

不需要为这段摘要单独写报告文件。

## Hard Stop — 出现以下情况必须停

- 总纲 / 正式评审 / 当前代码出现无法自行判断的冲突。
- 必须修改上游已经 PASS 的核心状态/路由语义才能继续。
- 发现任务卡要求实际依赖尚未拍板的产品定义。
- 当前分支发生并行修改，无法安全判断共享文件最终版本。
- 旧原型关键功能证据缺失，继续只能靠猜。

以上情况直接报告评审线程，不允许“先做一个看起来合理的版本”。
