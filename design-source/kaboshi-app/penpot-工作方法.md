# Penpot 做原生 App 设计的工作方法

> 结论先行：交付对象是 iOS/Android 原生开发时，交付物必须是 Penpot 设计稿（带标注、token、切图），HTML 不能作为交付物，只用于早期概念验证。

## 1. 交付立场

- 原生开发用 SwiftUI/UIKit、Jetpack Compose/XML，不认 HTML/CSS。
- HTML 稿对开发只是"能点的参考图"，间距/颜色/切图全靠自己扒，等于甩锅。
- 正式交付走 Penpot：图层结构化、组件化、颜色字体建成 token、画板按逻辑点出图、多倍切图导出。开发用 Penpot 的 Code/标注模式直接读数值、拷颜色、下切图。
- HTML 仅用于：早期快速验证视觉方向、动效演示、高保真概念、跑真实交互/响应式。确认方向后落到 Penpot 做正式交付。

## 2. 能力边界

### Penpot 擅长
- 代码化建图层、画板、组件，批量生成重复结构（列表、卡片、表单）
- Flex/Grid 自动布局排版
- 组件库、颜色、字体样式、变体、Design Token
- 导出 PNG/SVG 切图
- 通过 `execute_code` 操作，通过 `export_shape` 出图自检
- `generateStyle` / `generateMarkup` 对图层生成 CSS/SVG 标记

### Penpot 不擅长 / 做不到
- 手绘风插画、复杂 Path、布尔运算（代码写起来极费劲）
- 像素级精细打磨（1~2px 差异靠肉眼从截图估，不准）
- 页面间 prototype 交互连线（API 支持有限）
- 强创意、强视觉冲击的首发级 KV（出品不稳定）

## 3. 视觉闭环（核心，治"眼瞎"）

每改一版必须"看"一眼成品，形成闭环：

1. 写代码生成/修改图层
2. `export_shape` 导出画板或组件为 PNG（Penpot 场景优先用这个，回路最短）
3. 读取图片检查
4. 定位问题并修改
5. 重复直到收敛（常规屏通常 3~5 轮）

### 用什么看
- Penpot 稿：用 `export_shape` 直接导出 PNG/SVG 看，不必开 Chrome
- HTML/响应式：用 Chrome 截图核对
- 检查重点：溢出/裁切、层级遮挡、间距对齐、颜色字号圆角、缺元素/顺序反、布局塌了、Flex 没撑开、auto 高度算错

### 对照指定参考设计核查（必做）
- 用户指定 traeDesign / 参考稿后，每轮导出必须与参考设计逐项对照，不靠"感觉差不多"。
- 核查清单：
  1. 整体布局结构（区块顺序、分栏、导航/内容/Tab 位置）
  2. 间距体系（区块间距、卡片内边距、元素间距是否与参考一致）
  3. 颜色（主色/辅色/背景/文字/分割线，优先用共享 token，不自行取色）
  4. 字体（字号、字重、行高、字间距、对齐）
  5. 组件形态（圆角、边框、阴影、图标位置、状态样式）
  6. 内容（文案、图片占位、数字、空状态/错误状态是否齐全）
- 发现不一致直接改，不把"对不齐"留给用户挑。
- 参考设计可能是截图、现有 Penpot 画板、或设计规范；以用户指定的那份为准。

### 闭环的局限（要诚实告知用户）
- 看到的是栅格图，不是可量测画布，1~2px 差异看不准，最终数值以 Penpot 标注面板为准
- 截图能避免丑得离谱，但不保证一次到位，审美判断仍需用户反馈
- 复杂屏迭代轮数多，比人手拖慢，但比盲写靠谱

## 4. 单屏工作流

1. 确认：什么 App、哪个页面、配色/风格偏好
2. 建画板：390×844（iPhone 逻辑点），必要时加 Android 常见尺寸
3. 建 token：颜色、字号/字重/行高建成 library color / typography，用变量名
4. 建组件：按钮、输入框、卡片、列表项等，带 default/pressed/disabled 状态
5. 组合页面：用 Flex 布局，状态栏/导航栏/内容区/底部 Tab 分层清晰
6. 走视觉闭环：导出 → 看图 → 改 → 再导出
7. 交付自检：进 Code/标注模式点几个元素，确认尺寸(pt/dp)、字号(sp)、颜色(hex/变量)、圆角、阴影、切图都能直接被开发读取

## 5. 给原生开发的交付清单

- 画板按逻辑点（390pt 基准），非物理像素
- 颜色：hex + token 变量名，必要时给暗黑模式
- 字体：字号、字重、行高、字间距（sp / Dynamic Type 友好）
- 间距/圆角/阴影：精确数值
- 图标/位图：@2x/@3x（iOS）、xxhdpi（Android），命名规范
- 组件状态：default / pressed / disabled / selected
- 适配说明：不同屏幕尺寸、安全区、横屏规则（如需要）

## 6. 沟通原则

- 不替 HTML 辩护，交付对象是原生就老实做 Penpot
- 不空谈能力，能练就直接搭一屏让用户和开发检验
- 边界提前讲清，不夸大审美和精细度上限
- 用户给方向，我负责结构化生成 + 视觉闭环迭代

## 7. 跨线程交接协议（重要）

新线程不记得之前的对话，所有约定必须写进文件，开工前先读。

### 三个外置文件（都存在工作区）
- `penpot-工作方法.md`：本文档，讲方法和底线，基本不变。
- `项目约定.md`：本项目的具体事实，随项目推进持续追加。
- 各批次的截图/导出图：存在工作区，供视觉对照。

### `项目约定.md` 必须记录
- Penpot 文件地址、团队/文件 ID、共享 token 库名称
- 原型链接（Mockplus 分享地址）、原型分组与页面清单
- 第一批/当前批范围（哪些页面）
- 已建好的画板、组件、token 清单（名字 + 在哪一页）
- 素材图来源/风格约定（哪些图已替换、用什么风格）
- 已拍板的修改和不要重做的东西
- 踩过的坑、开发反馈、待办
- 下一步该做什么

### 开新线程的标准开场（用户照这样发）
1. 告诉它："先读工作区里的 `penpot-工作方法.md` 和 `项目约定.md`"
2. 说明这批要做的页面范围（从原型哪个分组、哪几屏）
3. 说明产出位置：在指定 Penpot 文件的哪个页面建画板
4. 要求它先复述从文件里读到的关键事实，确认无误再动手
5. 做完后让它把新增/修改的组件、token、待办追加回 `项目约定.md`

### 每个线程的职责边界
- 一个线程只做一批（8-10 屏，或一个完整模块）
- 只追加 `项目约定.md`，不改 `penpot-工作方法.md`
- 组件能复用就复用 Penpot 里已有的，不重复造；要新建组件先在 `项目约定.md` 里查有没有
- 开工前先连 Penpot、读共享 token 库、看已有组件和画板，再动手
- 每屏走视觉闭环，导出图对照原型核查

### 主线程（第一个对话）的职责
- 定方法、定第一批范围、连 token、搭标杆屏和核心组件
- 建好 `项目约定.md` 的初始结构
- 标杆屏经用户/开发确认后，后续批次才开新线程铺开
- 标杆没确认前，不要批量开线程，避免错误被复制到几十屏

### 不要做的事
- 不要在一个线程里硬扛 60-70 屏
- 不要让新线程"凭感觉"接，不给文件就读懂上下文
- 不要每个线程自己造一套颜色/字号/组件名
- 不要跳过视觉闭环直接交付
